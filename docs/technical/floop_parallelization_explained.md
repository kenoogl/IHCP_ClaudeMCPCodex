# @floopによる3重ループ並列化の詳細解説

**作成日時**: 2025年10月23日
**対象コード**: `@floop backend for k in 2:SZ[3]-1, j in 2:SZ[2]-1, i in 2:SZ[1]-1`

---

## 📚 基本概念

### @floopとは
FLoops.jlパッケージが提供する並列ループマクロで、複雑な多重ループを簡潔に並列化できます。

```julia
using FLoops

# 逐次実行
@floop SequentialEx() for i in 1:N
    # 処理
end

# 並列実行（ThreadsX.jl使用）
@floop ThreadedEx() for i in 1:N
    # 処理
end

# バックエンド動的切り替え
backend = get_backend(par)  # par="thread" or "sequential"
@floop backend for i in 1:N
    # 処理
end
```

## 🔄 3重ループの並列化メカニズム

### ステップ1: ループの平坦化（Flattening）

3重ネストループを1次元の反復空間に変換します。

```julia
# 元のコード
@floop backend for k in 2:nk-1, j in 2:nj-1, i in 2:ni-1
    array[i,j,k] = f(i, j, k)
end

# 内部的には以下のように変換
# 総反復回数 = (ni-2) × (nj-2) × (nk-2)
```

#### 具体例（プロジェクトの格子サイズ）
- `ni = 80`, `nj = 100`, `nk = 20`
- 反復範囲: `i in 2:79`, `j in 2:99`, `k in 2:19`
- 各次元の反復回数: `78 × 98 × 18`
- **総反復回数**: `137,592回`

### ステップ2: チャンク分割（Work Splitting）

総反復回数をスレッド数で均等分割します。

```
8スレッドの場合:
  チャンクサイズ ≈ 137,592 ÷ 8 = 17,199回/スレッド

各スレッドの担当範囲:
  Thread 1: 反復     1 ~  17,199
  Thread 2: 反復 17,200 ~  34,398
  Thread 3: 反復 34,399 ~  51,597
  Thread 4: 反復 51,598 ~  68,796
  Thread 5: 反復 68,797 ~  85,995
  Thread 6: 反復 85,996 ~ 103,194
  Thread 7: 反復103,195 ~ 120,393
  Thread 8: 反復120,394 ~ 137,592
```

### ステップ3: 線形インデックスから多次元インデックスへの変換

各スレッドは、割り当てられた線形インデックスを(i, j, k)に変換して処理します。

```julia
# 線形インデックス n から (i, j, k) への変換
# （内部的な疑似コード）

ni_range = 78  # 2:79の範囲
nj_range = 98  # 2:99の範囲

# n = 1の場合 → (i=2, j=2, k=2)
# n = 78の場合 → (i=79, j=2, k=2)
# n = 79の場合 → (i=2, j=3, k=2)
# ...

for n in my_chunk_start:my_chunk_end
    # 線形インデックスから3次元インデックスを計算
    n_adjusted = n - 1  # 0始まりに調整

    # k方向のインデックス（最も外側）
    k_idx = div(n_adjusted, ni_range * nj_range) + 2
    remainder = mod(n_adjusted, ni_range * nj_range)

    # j方向のインデックス（中間）
    j_idx = div(remainder, ni_range) + 2

    # i方向のインデックス（最も内側）
    i_idx = mod(remainder, ni_range) + 2

    # 実際の処理
    array[i_idx, j_idx, k_idx] = f(i_idx, j_idx, k_idx)
end
```

## 🎯 実際の処理の様子

### 8スレッドでの並列実行イメージ

```
格子空間 (80×100×20):
┌─────────────────────────────────────┐
│ Thread 1が処理する(i,j,k)の範囲    │
│ k=2, j=2~99, i=2~79の一部           │ ← 約17,199セル
├─────────────────────────────────────┤
│ Thread 2が処理する(i,j,k)の範囲    │ ← 約17,199セル
├─────────────────────────────────────┤
│ Thread 3が処理する(i,j,k)の範囲    │ ← 約17,199セル
├─────────────────────────────────────┤
│ ... （Thread 4~7）                  │
├─────────────────────────────────────┤
│ Thread 8が処理する(i,j,k)の範囲    │ ← 約17,199セル
└─────────────────────────────────────┘

各スレッドは独立して異なるセルを処理するため、
データ競合は発生しません。
```

## ⚙️ 並列化のメカニズム詳細

### 1. FLoops.jlの内部動作

```julia
# @floopマクロ展開後の疑似コード
function parallel_loop(backend, ranges...)
    # 反復空間の計算
    total_iterations = prod(length.(ranges))

    # スレッド並列実行
    Threads.@threads for tid in 1:Threads.nthreads()
        # 各スレッドの担当範囲を計算
        chunk_size = div(total_iterations, Threads.nthreads())
        start_idx = (tid - 1) * chunk_size + 1
        end_idx = tid == Threads.nthreads() ? total_iterations : tid * chunk_size

        # 担当範囲の反復を実行
        for n in start_idx:end_idx
            # 線形インデックス → 多次元インデックス変換
            indices = linear_to_cartesian(n, ranges)
            # ユーザー定義の処理を実行
            process(indices...)
        end
    end
end
```

### 2. ThreadsX.jlによる最適化

FLoops.jlはThreadsX.jlをバックエンドとして使用し、以下の最適化を自動適用：

- **動的負荷分散**: ワークスティーリング（work-stealing）
- **チャンクサイズ最適化**: キャッシュ効率を考慮した分割
- **False Sharing回避**: スレッド間のキャッシュライン競合を最小化

---

## 📊 並列化効率の要因

### ✅ 効率が高い理由

1. **データ並列性**: 各反復が完全に独立
   - 異なる(i,j,k)への書き込み → データ競合なし
   - 同期不要 → オーバーヘッド最小

2. **均等負荷分散**: 全スレッドがほぼ同じ作業量
   - 137,592回 ÷ 8 = 17,199回/スレッド
   - 負荷の偏りがない

3. **キャッシュ効率**: 連続メモリアクセス
   - 配列の連続領域にアクセス
   - L1/L2/L3キャッシュの有効活用

### ⚠️ 効率が低下する要因

1. **並列化オーバーヘッド**
   - スレッド生成・管理コスト
   - ワークスケジューリングのコスト
   - 同期バリアのコスト

2. **メモリバンド幅の競合**
   ```
   8スレッド同時実行時:
   - 各スレッドがメインメモリにアクセス
   - メモリバンド幅が飽和
   - 実効メモリ帯域 < 理論値
   ```

3. **False Sharing（偽共有）**
   ```
   キャッシュライン境界:
   Thread 1: array[i,   j, k] ─┐
   Thread 2: array[i+1, j, k] ─┴─ 同じキャッシュライン

   → 両スレッドがキャッシュラインを無効化し合う
   → 性能低下
   ```

4. **問題サイズ依存**
   ```
   小規模問題（nt=10）:
   - 並列化オーバーヘッドが支配的
   - 4スレッドで飽和（32.93秒）
   - 8スレッドで性能低下（33.99秒）

   大規模問題（nt=100予測）:
   - 計算量がオーバーヘッドを上回る
   - 8スレッドでも効率向上
   - 理論的には効率50-60%に改善
   ```

## 🔬 Phase 5測定結果との対応

### 小規模問題（ni=80, nj=100, nk=20, nt=10）

| スレッド数 | 各スレッドの反復回数 | 実行時間 | スピードアップ | 効率 |
|-----------|-------------------|---------|--------------|------|
| 1         | 137,592           | 97.38秒 | 1.00倍       | 100% |
| 2         | 68,796            | 53.64秒 | 1.82倍       | 91%  |
| 4         | 34,398            | 32.93秒 | 2.96倍       | 74%  |
| 8         | 17,199            | 33.99秒 | 2.86倍       | 36%  |

### 効率低下の解釈

1. **2スレッド（効率91%）**:
   - オーバーヘッドが小さい
   - メモリバンド幅に余裕
   - False Sharingの影響が小さい

2. **4スレッド（効率74%）**:
   - オーバーヘッドが増加
   - メモリバンド幅が制約に
   - 最速実行時間を達成

3. **8スレッド（効率36%）**:
   - オーバーヘッドが支配的
   - メモリバンド幅が飽和
   - チャンクサイズが小さすぎる（17,199回）

## 💡 最適化のヒント

### 1. 問題サイズの拡大
```
大規模問題（nt=100予測）:
  総反復回数 ≈ 137,592 × 10 = 1,375,920回
  8スレッド: 171,990回/スレッド

  → チャンクサイズが大きくなる
  → オーバーヘッドの相対的な減少
  → 効率向上（36% → 50-60%予測）
```

### 2. 前処理器の選択
```
GS前処理器（小規模問題）:
  8スレッド効率: 36%

Jacobi前処理器（Phase 4データ）:
  8スレッド効率: 42%

  → Jacobiの方が並列化に適している
  → 2バッファ方式でFalse Sharing回避
```

### 3. チャンク戦略のカスタマイズ
```julia
# デフォルト: 自動分割
@floop backend for k in 2:nk-1, j in 2:nj-1, i in 2:ni-1
    # 処理
end

# カスタムチャンク（例）:
# 外側ループ（k方向）だけを並列化
Threads.@threads for k in 2:nk-1
    for j in 2:nj-1, i in 2:ni-1
        # 処理
    end
end

→ キャッシュ局所性の向上
→ False Sharing軽減
```

## 📚 まとめ

### @floopの並列化の仕組み
1. 3重ループを1次元反復空間に平坦化
2. 反復回数をスレッド数で均等分割
3. 各スレッドが線形インデックスを(i,j,k)に変換して処理
4. データ競合なし、同期不要の完全並列実行

### 実測性能との整合性
- ✅ 2スレッド: 高効率（91%）→ オーバーヘッド小
- ✅ 4スレッド: 最適（74%）→ 計算量とオーバーヘッドのバランス
- ⚠️ 8スレッド: 飽和（36%）→ 小規模問題の限界

### 実用的な推奨
- **小規模問題**: 4スレッドが最適
- **大規模問題**: 8スレッドで効率向上予測
- **前処理器**: Jacobiの方が並列化に適している
